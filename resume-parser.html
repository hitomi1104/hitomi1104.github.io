Resume Parser: Turning Any Resume Format into Structured, Scored Data

Introduction

Recruiters and HR systems receive resumes in every format: designed PDFs, Word files, scanned pages, phone photos, and LinkedIn profiles. Most parsers handle one format well and quietly fail on the rest, and when they fail, they rarely say which fields they guessed. I built this resume parser to handle all of these formats through one API and to report how confident it is in every field it extracts.

Description

The Resume Parser is a working proof-of-concept API built with FastAPI. It accepts a resume in any common format, sends it to the right extraction engine, and returns structured JSON with ten fields (name, email, phone, LinkedIn, GitHub, location, summary, skills, education, and work experience). Each field comes with its own confidence score, plus an overall score for the whole resume.

Objective

My goal was to test whether a hybrid approach, using a text extractor or an OCR model depending on the input and then an LLM for field extraction, could handle every common resume format through a single API. I also wanted the system to be honest about uncertainty, so a reviewer knows which fields to check instead of trusting every output equally.

Process

  1. Built an extractor for each format. PyMuPDF reads PDFs, python-docx reads Word files, LandingAI's OCR reads images, and headless Selenium scrapes LinkedIn profiles.
  2. Cleaned the text before sending it to the model. PDF extraction often splits one sentence across several lines. A preprocessing step joins broken lines, unifies bullet characters, and removes extra spaces so the model sees readable text.
  3. Designed the extraction prompt. The prompt asks GPT-3.5 for ten fields, each as a value plus a confidence score, at a low temperature (0.2) for more consistent output.
  4. Made failures visible. Unsupported file types return a clear error, and if the model's reply isn't valid JSON, the API returns the raw output instead of a half-filled result.
  5. Tested and documented limits. I tested each endpoint through FastAPI's built-in Swagger page with sample resumes and recorded the failure modes I found (see below).
  6. Revised it for this portfolio. I turned the project's technical notes into a case study for a broader audience, with a workflow diagram, a plain-language explanation, and an honest list of known issues.

Value Proposition

The Resume Parser saves recruiters and HR teams from retyping resume data by hand, whatever format a resume arrives in, and shows them exactly which fields to double-check. Instead of trusting a black box, reviewers get structured data with a confidence score on every field.

Unique Value

  • One API for every format. Text files, images, and LinkedIn URLs each go to the engine best suited to them instead of forcing everything through one model.
  • Confidence on every field. Reviewers can focus on the low-confidence fields instead of rechecking everything.
  • Honest about its limits. Known failure modes, such as LLM hallucination and scraping blocks, are documented rather than hidden, which is what a real deployment needs.

Relevance

Turning unstructured documents into reliable, structured data is one of the most common ways organizations use AI today, in hiring, healthcare, finance, and regulatory work. This project shows that I can combine LLMs with OCR and traditional extraction tools, design for uncertainty, and evaluate a system's weaknesses honestly. These are the same skills I use in my work on a federal healthcare regulatory program and the skills applied and forward-deployed AI engineering roles call for.
